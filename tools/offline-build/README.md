# Оффлайн-сборка jar без Gradle и интернета

Обычная сборка мода тянет из сети сотни мегабайт: Minecraft, маппинги, Fabric
Loom или ModDevGradle, сам Gradle. Если maven-репозитории недоступны, это
тупик — но не для компиляции как таковой. Здесь лежит инструментарий, который
собирает настоящие jar-файлы мода в изолированной среде.

## Идея

JVM связывает вызовы **по имени класса и дескриптору метода**, а не по коду
библиотеки. Значит, чтобы получить корректный байткод, компилятору достаточно
знать *объявления* API Minecraft и загрузчика — тела методов не нужны.

Поэтому в `stubs/` лежит набор заглушек: ~90 файлов, описывающих ровно те
классы, поля и методы 1.21.1, к которым обращается мод, с точными сигнатурами.
Мод компилируется против них, а в jar попадают только классы мода — заглушки
отбрасываются. В игре их место занимают настоящие классы Minecraft.

Тонкий момент — **стирание типов**. Например, `BlockState#setValue` объявлен в
`StateHolder<O, S>` как `<T extends Comparable<T>, V extends T> S setValue(Property<T>, V)`,
и его дескриптор в байткоде — `(Property;Comparable;)Object`. Заглушка повторяет
эту иерархию и обобщения, иначе JVM не нашла бы метод. То же касается
`ItemStack#get/set`, `Registry#register`, `DeferredHolder#get` и других.

## Инструменты

| Что | Откуда берётся |
|---|---|
| JVM (Java 25, Temurin) | pip-пакет `jdk4py` — обычное колесо с PyPI |
| Компилятор ECJ 3.39 | jar Eclipse-компилятора из git-дерева публичного репозитория |
| Упаковка jar | модуль `zipfile` из стандартной библиотеки Python |

Полноценный JDK не нужен: `jdk4py` даёт только среду выполнения (без `javac`),
а компилятором работает ECJ — он написан на Java и запускается на этой же JVM.
`jar` тоже не нужен: jar — это zip с `META-INF/MANIFEST.MF`.

## Ремап Fabric-сборки

Fabric в продакшене знает классы Minecraft под intermediary-именами
(`net.minecraft.class_1935`), поэтому мод, собранный в Mojang-именах, падает с
`NoClassDefFoundError: net/minecraft/world/level/ItemLike`. Обычно переименованием
занимается Loom; здесь это делает `fabric_remap.py` по цепочке
**mojmap → yarn → intermediary**:

* соответствие yarn → intermediary берётся из репозитория `FabricMC/yarn` (ветка 1.21.1);
* соответствие mojmap → yarn задано таблицами в скрипте и **проверяется дескрипторами**:
  имя должно найтись у нужного класса, а типы параметров совпасть. Не совпало —
  сборка останавливается с ошибкой, битый jar не выпускается;
* неоднозначности (одно имя у нескольких классов) тоже приводят к ошибке, пока
  в таблице не указан класс-объявитель.

Отдельная история — константы вроде `Blocks.LIGHT` или `SoundEvents.LEVER_CLICK`:
их intermediary-имена (`field_10524`) генератор имён Yarn вычисляет по содержимому
реестров, в текстовых маппингах их нет. Такие обращения перенаправляются на
класс-мост [`fabric-extra/.../VanillaRefs.java`](fabric-extra/by/strasse/strassemods/compat/VanillaRefs.java),
который берёт значения из самих реестров по идентификаторам (`minecraft:light`)
и константы перечислений через `valueOf` — то и другое не обфусцируется.
Идентификаторы сверены с дампами реестров Mojang.

Сам ремап правит только пул констант: новые UTF8-записи дописываются в конец,
ссылки переставляются, индексы существующих записей не меняются — поэтому байткод,
`StackMapTable` и `BootstrapMethods` остаются валидными.

## Использование

```bash
# 1. поставить JVM, компилятор и маппинги (в /tmp/strassemods-offline)
./tools/offline-build/fetch-toolchain.sh

# 2. собрать jar'ы в dist/
python3 tools/offline-build/build.py --all --out dist

# 3. проверить результат
python3 tools/offline-build/verify.py --report tools/offline-build/api-usage.txt dist/*.jar
```

Переопределить пути к инструментам можно переменными окружения
`OFFLINE_BUILD_JAVA`, `OFFLINE_BUILD_ECJ`, `OFFLINE_BUILD_WORK`.

## Что проверяется

`verify.py` разбирает пул констант каждого класса и выписывает все обращения к
Minecraft, NeoForge, Fabric и slf4j — с дескрипторами. Отчёт лежит в
[`api-usage.txt`](api-usage.txt); именно его нужно сверять с исходниками 1.21.1,
если что-то не заработает. Затем он просит JVM загрузить и верифицировать каждый
класс: это ловит битый байткод и структурные ошибки.

## Ограничения

* **Fabric.** Сборка проходит ремап в intermediary и годится для продакшена, но
  каждое соответствие имён — результат сверки таблиц с маппингами Yarn, а не работы
  Loom с настоящими jar'ами. NeoForge 1.21.1 работает на Mojang-именах, ему ремап не нужен.
* **Миксины** (`src/**/mixin/**`) в оффлайн-сборку не входят: им нужен
  препроцессор Mixin и refmap от Loom.
* Заглушки покрывают только тот API, который использует мод. Добавили в код
  новый вызов — допишите объявление в `stubs/`, иначе компиляция упадёт
  (это безопасный отказ: молча собрать неправильный вызов нельзя).
* Ни один тест не заменяет запуск игры. Эталонная сборка — `./gradlew build`
  или workflow `ci/build-magic-wand.yml`.
